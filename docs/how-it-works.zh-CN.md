# MAP 的工作原理

这里详细介绍各个角色和协调分支。协议本身以英文的 [PROTOCOL.md](../PROTOCOL.md) 为准；英文版和脚本命令见 [how-it-works.md](how-it-works.md)。

角色是一种职责，不是一个进程。同一个角色可以同时开多个会话：可以有多条开发线、多个 builder 和 reviewer，可以由几个 lead 按区域分工，也可以有几个发布会话，靠 `release-main` 这个认领轮流推进主分支。项目也可以自己增加角色，比如测试、文档、安全审计；但批准权始终只在负责人手里，也只有发布角色能推进主分支。见 PROTOCOL.md 2.1。

角色和权限都有默认设置，项目可以在 `AGENTS.md` 里调整：给角色改名、合并或去掉某些角色、改变谁能做什么，还可以定义自己的消息类型。这些调整怎么审批，在初始化时选定，默认是由 lead 汇总后请负责人批准；没写的就沿用默认值。有几条不能改：只有负责人能批准；同一时间只有一个会话推进主分支；一个工作目录只允许一个会话写；审查者不审自己写的改动。见 PROTOCOL.md 2.2。

agent 之间通过仓库里一个永不合并的孤立分支 `coordination` 沟通，上面放着状态文件、消息、任务认领和负责人的决定。一整条线也可以交给另一个 agent 或另一台机器：交出的一方把所有改动提交并推送，给自己的线名留下一份 `transfer` 交接单，然后结束；接手的一方用同一个线名启动，先读交接单，逐个核对分支的 SHA（PROTOCOL.md 5.7）。

每个会话加入时，会在状态文件里写清自己的环境：工具和版本、模型、机器标签、沙箱和网络权限、能跑什么和不能跑什么、新消息怎样唤醒它、能不能推送协调分支、负责人通常在不在场，以及用什么 git 身份提交（默认用线名，也可以统一用负责人的名字）。写好后通知所有人。这里不写主机名、IP 地址和任何密钥。`scripts/` 里的脚本只依赖 git 和 POSIX sh。

升级方法见 [UPGRADING.md](../UPGRADING.md)。从 2.0 版起，有新版本时 `session-start.sh` 和 `doctor.sh` 会提示一行（设 `MAP_UPDATE_CHECK=0` 可以关掉）；各个会话的版本不一致时，`doctor.sh` 还会给出警告。升级由 lead 负责：先用 `upgrade.sh --check <项目>` 列出会改动什么，再去问负责人。初始化时可以选择升级策略：手动、自动安装补丁版本，或自动安装次版本；遇到主版本，或者规则片段有变化，总是要先问负责人（PROTOCOL.md 12.3）。
